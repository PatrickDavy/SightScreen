1. Platform and architecture

Recommended stack

React Native with Expo (bare workflow), TypeScript. One codebase for both platforms, with native modules where the camera and inference demand it. The prototype's screen decomposition maps one-to-one onto React Native screens, and the component library translates directly — every primitive is styled from flat tokens with no CSS features that lack a React Native equivalent.

The bare workflow is required, not optional: 240 fps capture, thermal-state observation and on-device pose inference all need native code that Expo Go cannot host.

Offline-first is architectural, not a feature flag

Capture, inference, review and the workload ledger must all function fully in aeroplane mode. Treat the local SQLite database as the primary store and any server as a replica. There is no loading spinner anywhere in the core loop that waits on a network call — sync queues silently and never blocks a screen.

Non-negotiable in the MVP regardless of scope pressure

The age gate (S02), guardian consent (S03), the workload ledger (S50) and confidence flagging on every speed estimate. These four are the ethical floor. Retrofitting them later means retrofitting them onto real minors' data, which is both a compliance problem and a trust problem that does not recover.

Navigation

Four tabs with an oversized centre capture action: Home · Improve · ● Bowl · Load · You. Capture, onboarding, the paywall and delivery detail are modal contexts outside the tab bar — capture is a mode, not a place, and hides the bar entirely.

Implement with React Navigation: a bottom tab navigator whose centre item is a custom oversized button dispatching to a modal stack, plus a root stack for the modal contexts. The prototype models this with a view stack (push / pop / setTab in index.html); its back semantics — a tab change clears the stack, a detail push preserves it — are the intended behaviour.

Two invariants worth an automated test

No bare measured number. Any measured value rendered without a band prop on Metric is a bug. Speeds show as 128 ± 4 km/h, never 128.4 km/h.

Sentence case, no emoji. Uppercase is reserved for small tracked eyebrow labels. No exclamation marks in product copy.

4. Capture — the crux

Capture carries the expensive failure modes: a silent failure costs a bowler an entire spell they cannot re-bowl. Build this flow first and instrument it hardest.

S21 Placement checks

Four live validations, each with a plain-language fix, all overridable with the consequence stated:

CheckSignalFailure copy
Landscape orientationInterface orientationTurn the phone landscape — side-on to the pitch.
Device levelAccelerometer, ±3° toleranceTilt it back to level, or speeds will read low.
Crease and stumps visibleCalibration state for this venueMark them once — remembered for this venue.
Light for 240 fpsExposure duration / ISO ceilingToo dark for slow motion. Move to better light or the speed reading will be unreliable.

An overridden check marks every delivery in that session confidence: low. Overriding is allowed; hiding the consequence is not.

S22 Calibration

Two taps — popping crease line, then base of the stumps — resolved against known pitch geometry (22 yd pitch, 1.22 m crease) to produce the scale used for run-up and ball speed. Persist per venue keyed on a camera-pose fingerprint so a returning bowler at their home nets skips the step. Fallback when the stumps cannot be seen: manual pitch-length entry.

S24 Recording — the distance-legible screen

Read at 20 metres in sunlight. It carries a full-screen colour state, a delivery counter, and nothing else.

StateColourMeaningAudio
Armed / recordingTurf #2F6B3C, full bleedRecording, detection healthySoft tone per detected delivery; optional spoken speed
ProblemAmber #A56E00, full bleedOut of frame · no detection for 90 s with motion · overheating · storage lowDistinct alert tone plus a spoken reason
StoppedCherry #B02A19, full bleedSession endedEnd tone
  • Counter type — the largest legible size the screen allows; the prototype uses ~190px display weight 700 at 390pt width. Scale with screen width, do not cap at a comfortable indoor size.
  • Contrast — specify against outdoor luminance, not the indoor 4.5:1 ratio. Full-brightness override for the duration of capture; screen never dims or sleeps.
  • Audio is the primary channel. It works when the screen does not — facing away, mid-follow-through, walking back to the mark. Every state change has a distinct sound; the whole session is operable by ear.
  • No controls. Ending is a tap anywhere, or automatic after five minutes without a detected delivery.

Thermal and power policy

Degrade, never stop. On a serious thermal state, drop the capture rate rather than ending the session, switch to amber, announce the trade-off aloud, and record the event on the session so review can explain the wider error bands honestly. Pre-flight on S23 gives a realistic capacity estimate from battery and thermal headroom ("Room for about 45 deliveries at 62% battery") and warns below 20%.

Error matrix

The full condition list is section 7 of the flow spec and is normative. Two rules govern all of it: failures are announced aloud at the moment they occur, and captured footage is never lost — interrupted processing resumes on relaunch.

Compliance to confirm before launch

UK Age Appropriate Design Code, GDPR Article 8 (and the applicable national age of digital consent, 13–16 by territory), COPPA if the US is in scope, and both app stores' kids/minors policies. Data minimisation for under-18 accounts is a design constraint already reflected above; verify the retention periods and the consent record-keeping with counsel.

6. Inference and measurement honesty

  • On device, always. Video does not leave the phone in the MVP. This is the privacy position and the offline requirement in one decision.
  • Error bands are model output, not decoration. Every speed and every angle carries an uncertainty computed from frame count, calibration quality, light and pose confidence. Surface the band everywhere the value appears.
  • Confidence flagging is immutable and consequential. Low-confidence deliveries stay visible in lists, are excluded from trends, and never feed an insight.
  • Implausible values are flagged, not hidden. A speed outside the plausible range is marked low-confidence, dropped from trends, and shown alongside the raw video so the bowler can judge it themselves.
  • One insight per session. The determinant set is deliberately small — front knee at release, run-up speed, arm delay, trunk flexion. When two limiters are close, choose the safer and easier one and say why on S33.
  • Every metric explains itself. S32 carries what it is, why it links to speed, how it is measured here, the measurement's limitations, and the citation. The research summary is a product surface, not a footnote.

Validation gate before any speed number ships

Speeds must be validated against radar over a range of light conditions, phone models and distances, and the published error band must be the measured one. The credibility risk here has already damaged a competitor; a band that flatters the model is worse than no number.

7. Accessibility and field conditions

  • Touch targets 60×60 pt minimum on anything used outdoors — above both platforms' guidance, because the user is standing, hot and hurried.
  • One-handed — all pre-capture controls in the lower two-thirds of the display; the other hand holds a ball.
  • Audio-first — the capture session is fully operable by ear, which serves the 20-metre problem and blind or low-vision users with the same mechanism.
  • Screen readers — every IconButton ships its label; measured values announce as "116.2 plus or minus 2.3 kilometres per hour", not as raw glyphs.
  • Reduced motion honoured; no animation carries information alone. Colour is never the only signal — every capture state has an accompanying sound and word.
  • Dynamic type — support at least to the platform's large accessibility sizes on review and settings screens; the recording counter is already at maximum.
  • Units — km/h and mph selectable throughout; the UK market matters commercially and thinks in mph. Metric and imperial for height and span too.

9. Commercial rules

  • Free tier — three analysed sessions a month, the full speed log, the complete workload ledger. The ledger is never gated, on any tier, at any time.
  • Pro — unlimited analysis, full metric breakdown, retest comparisons, trends, drill library, export.
  • Paywall placement — the fourth analysed session of a calendar month; never inside first run, never before the loop has been completed once. Secondary triggers: a locked deep-metric view after the allocation is spent, and retest export.
  • Presentation — annual price first, monthly equivalent beneath, no countdown timer. Annual retention runs roughly 2.5× monthly, so push annual by making it obviously better value rather than by manufacturing urgency.
  • Store implementation — StoreKit 2 and Google Play Billing 6+, receipt validation server-side, entitlement cached locally so an offline user keeps what they paid for.

10. Build order

  1. Foundations — token module, font bundling, component port, navigation shell, SQLite schema. Nothing user-visible; everything downstream depends on it.
  2. Capture spine — S20→S26 with real 240 fps capture, placement checks, calibration, the distance-legible recording screen and audio cues. Ship this to a field test before any analysis exists; if hands-free capture does not work at 20 metres, the product changes shape.
  3. Inference and review — pose pipeline, speed with a validated band, confidence flagging, S30→S33. Radar validation gate sits here.
  4. Safety — age gate, guardian consent, workload ledger with manual entry, rest guidance. Non-negotiable for the beta.
  5. Improve loop — S40, S41 and a small hand-authored drill set, one per determinant.
  6. Post-beta — trends, season view, retest comparison, drill library breadth, coach linking, sharing, paywall.

11. Open questions for the beta to answer

These are asserted by the specification and unproven. Instrument each one; do not design past them.

  1. Is audio confirmation audible at 20 m in wind, with nets, other players and traffic? If not, the hands-free model needs a rethink — a paired watch is the leading alternative and would change the capture architecture.
  2. Does two-point calibration survive a hurried user in bright sun, or does it need automatic crease detection to be usable?
  3. What is the real thermal ceiling? If a phone sustains only 20 deliveries of 240 fps capture plus inference, the session model changes fundamentally — possibly to capture-now, process-overnight-on-charge.
  4. Does the delivery counter alone satisfy mid-session curiosity, or do bowlers walk back and break the flow? Test with and without spoken speed.
  5. Is one insight too austere? Test against a two-or-three variant, but resist the dashboard.
  6. Does the drill-check session type get used? If the retest is skipped the loop does not close and the product is a speed gun with extra steps.

Known prototype fakes — do not port

The countdown is shortened to five seconds regardless of setting; deliveries arrive on a 3.8-second timer; speeds are synthesised; video areas are flat ink blocks with no footage; calibration persists for the session only; the amber alert fires on a fixed 13-second timer to demonstrate the state. Workload guideline figures (7 overs a spell, 21 a week) are illustrative placeholders — replace with the real Cricket Australia 1-3-5 / 2-4-6 and ECB territory equivalents, sourced and dated, before any user sees them.

Gaps to resolve with the brand owner

No logo exists — the wordmark is set in type wherever a mark would go. Brand fonts are open-licence substitutes. There is no illustration library, no drill footage and no marketing surface. None of these block the build; all of them block a launch.
